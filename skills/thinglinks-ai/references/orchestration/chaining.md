# 串联规律

跨工具成立的规律,写进单个工具说明里都不完整,不遵守会得出看着合理的错误答案。

## 先拿标识,再查详情

对象靠标识定位,不靠名字。**设备名与分组名是加密列,不能当查询条件。**

| 要什么 | 入口 |
| --- | --- |
| `deviceIdentification` | `list_devices`(按产品/分组/连接状态筛) |
| `groupId` | `list_device_groups` |
| `productIdentification` | `get_device` 的返回 |
| `orgId` | `list_org_tree` |
| `employeeId` | `list_employees` |
| `alarmIdentification` | `get_alarm_records` |
| `taskId` | `list_ota_upgrade_tasks` |
| `traceId` | `get_data_bridge_traces` 清单模式 |
| `projectIdentification` | `list_view_projects` |

用户说「叫 xx 的那台」时,用产品或分组缩小范围,再在返回的名称里认。
把名字当筛选条件传,拿到的空结果会被读成「没有这台设备」。

## 三条前置查询

| 要做什么 | 必须先做 | 否则 |
| --- | --- | --- |
| 对数值下判断 | `get_thing_model` 拿单位与量程 | 只能猜这个值合不合理 |
| 查影子或时序 | `get_device` 一次 | 缓存链路上没有别处能兜住组织级收窄,范围会偏宽 |
| 判断某条规则该不该报 | `list_rule_conditions` 按产品查 | 按设备查是精确匹配,漏掉产品级条件 |

## 相对时间先落成绝对区间

时间参数与返回都用 `yyyy-MM-dd HH:mm:ss`,**不带时区,按平台时间理解**。

用户说「昨天」「最近」「上周」时,先换算成具体起止时间再查,并在回答里写出实际用的区间 ——
不写出来,用户无法判断你查的是不是他要的那一段。跨时区或跨班次的场景先问清楚,不要猜。

- 起止时间成对出现,只给一个不成立
- 有些工具收的是天数而不是起止,别混着传
- 返回里的日期字段可能只有日期没有时分秒,要精确时刻看创建时间

## 「所有设备」不要遍历

上限摆在那里:单次对比 20 台、单次统计 8 个属性、清单查询会截断。逐台调用既慢又必然撞上限。

| 用户说 | 做法 |
| --- | --- |
| 所有设备 / 全部 | 先用产品或分组把范围收敛,再在范围内查 |
| 这几台谁不正常 | 用横向对比一次查完,不要逐台调统计 |
| 超过单次上限 | 分批,并在回答里说明分了几批、覆盖多少台 |

清单带截断标记时**不能回答「一共多少台」**,也不能断定某台不存在。

## 上限与切分

| 查询 | 上限 |
| --- | --- |
| 影子带时间段 | 60 分钟 |
| 统计与横向对比 | 31 天 |
| 单次统计属性数 | 8 个 |
| 单次对比设备数 | 20 台 |

超限时工具会带着上限值与下一步报错,照做切分,不要改问法绕过。

## 截断的结果不能当全量

带截断标记时数量用 `total`,不要数 `records`;截断的清单不能用来断定某个对象不存在。
