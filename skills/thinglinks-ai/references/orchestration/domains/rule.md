# 规则、告警与桥接

## 选哪个

| 用户在问 | 用 |
| --- | --- |
| 这条规则为什么一直报警、阈值配得对不对 | `list_rule_conditions` |
| 最近有哪些告警、这个处理了吗、昨天报了多少次 | `get_alarm_records` |
| 这条规则跑了多少次、是不是变频繁了、执行慢不慢 | `get_rule_trigger_stats` |
| 数据为什么没进我的库、转发失败了多少次 | `get_data_bridge_traces` |

## 「为什么一直报警」要两个工具

告警记录给出是哪条规则(拿到告警标识),规则条件给出阈值与它所比对属性的单位量程。
只查其中一个都答不完整:只有告警记录 → 知道报了多少次但不知道该不该报;
只有阈值 → 不知道实际触发了多少。

再接 [metric](metric.md) 取该属性的实际取值区间,三者并排才能判定是真故障还是系统性误报。
完整顺序见 [workflows/rule/threshold-audit](../../workflows/rule/threshold-audit.md)。

## 告警记录接不回设备

平台没有为告警记录存设备身份。设备可能写在告警文案里,也可能没有 —— 那是人写的展示文案。
引用时要说「告警文案里写的是…」并让用户确认,**不能当成平台查证过的事实**。

## 按设备筛规则条件只是精确匹配

按设备标识筛不含「该产品全部设备」型的条件。筛出 0 条只说明没有专门为这台设备配的条件,
**不等于没有规则在盯它** —— 要看全请改按产品查。

## 失败态在三个工具里不一样

| 工具 | 有没有失败态 |
| --- | --- |
| 规则执行统计 | **没有**。只有 未执行/执行中/已完成,「未执行」是条件没命中,不是失败 |
| 桥接执行记录 | **有完整失败态**:成功/失败/部分成功/死信 |
| OTA(见 [ota](ota.md)) | **有**,失败台数就是真的失败 |

把规则那句「平台没有失败态」套到桥接或 OTA 上,会把真实的失败说成正常。反过来也一样。

规则跑很多次但很少出告警是正常的(条件没命中);告警远多于预期才要去看阈值与防抖。

## 桥接「卡在哪一步」只有单条模式答得了

不传追踪标识是清单模式;传了才有逐步骤明细。先用清单找到出问题的那一次,再回看步骤。
死信是重试都失败后进了死信通道,最该关注。
