# 设备与物模型

## 选哪个

| 用户在问 | 用 |
| --- | --- |
| 这台设备什么状态、在线吗、什么版本、是不是子设备 | `get_device` |
| 有哪些设备、哪些离线了 | `list_devices` |
| 车间/区域/某一批设备 | `list_device_groups` 拿 `groupId`,再传给 `list_devices` |
| 这个产品定义了哪些属性、单位和量程是多少 | `get_thing_model` |
| 这台设备现在各属性是多少 | `get_device_shadow` |
| 上次给它发的命令成功了吗 | `get_device_command_history` |
| 这条命令该怎么填、参数范围是多少 | `get_command_definition` |
| 这台设备在哪、某个市有哪些设备 | `list_device_locations` |

诊断任何设备问题的第一步都是 `get_device` —— 它同时给出在线状态、版本、网关归属,
后面三个方向(链路、版本、数据)都从这里分叉。

## 命令的三个工具答的是三件事

- `get_thing_model` —— 这个产品**有哪些**命令(只到命令名与说明)
- `get_device_command_history` —— **下发过**哪些、成功没有
- `get_command_definition` —— 某一条**怎么填**:参数类型、取值范围、是否必填、单位

判断「命令下发失败是不是参数填错了」要第三个。**单位尤其要看** —— 量纲对不上
是下发被拒或设备行为异常的常见原因。参数规格没并进物模型,是因为物模型返回本身已经上千 token,
把每条命令的参数全展开会翻几倍,而排查时通常只关心其中一条。

**没有下发命令的工具**。拿到参数规格后把下发交给用户在控制台执行,不要声称已经下发。

## 查不到位置不等于设备有问题

位置存在独立的表里、靠人工或导入录入,设备正常在线却没录位置是常态。
请求里给了、却没有位置记录的设备会原样进 `withoutLocation` ——
要说「这几台没有录入位置」,**不能说成「查不到这几台设备」**。

`list_device_locations` 不做地理计算。「离某点最近的设备」「两台相距多远」需要距离运算,
平台没有这个能力,不要拿经纬度自己估 —— 算出来的数看不出对错。要判断远近请把坐标交给用户。

行政区划编码是平台的区划码。用户说的是地名时,先按设备查、从返回里读出对应编码,不要自己猜。

## 易混:影子与时序

影子答「**现在**是多少」或「**那一刻**是多少」,始终是快照;
时序答「这段时间**怎么变的**」,返回的是序列。

用户问「温度这一小时怎么变的」而去调影子,会拿一个点的值描述一整段过程 ——
答案读起来完全合理,但它是错的。反过来,问「现在多少」去拉时序,贵且绕。

影子带时间段时会返回该区间的全部原始上报行,统计与判越限可以直接基于它算;
但快照值仍只是区间内最后一次上报,别拿它描述整段区间。

## 分组是「选中一批设备」的唯一实用入口

设备名不可搜,产品与连接状态又太粗。用户提到「车间」「某一批」时先拿 `groupId`。
分组名同样是加密列不能筛,要按名字找就把清单拉回来自己认。

空分组拿去筛设备会得到空结果 —— **这本身就是答案,不是查询失败**。

## 与其他域的接口

- 判断某个数值是否荒谬 → 先 `get_thing_model` 拿单位量程,再去 [metric](metric.md)
- 命令下发只读可查,**本服务不能下发**;用户要求下发时直接说明做不到
- 设备接入凭据(密码/密钥/证书)任何工具都不返回
