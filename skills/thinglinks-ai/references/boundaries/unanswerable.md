# 答不了什么

拿相近的数据凑一个听起来合理的答案,是这条链路上最常见的错误。下列情况显式说做不到。

| 用户会问 | 为什么答不了 | 该怎么说 |
| --- | --- | --- |
| 那条告警的通知发出去了没有 | 平台发通知时没回填关联业务字段,站内信与告警记录之间没有可靠关联 | 说明平台不记录这个关联;不要用时间接近去推断 |
| 这个配置被改成了什么值 | 操作日志只有元信息,没有请求参数与返回值 | 只能给「谁在什么时候改过什么对象」,新值去控制台看 |
| 哪个大屏在看某台设备 | 画布里不存设备绑定 | 只能给到组件的数据源地址;不要从组件标题里认设备 |
| 这条告警是哪台设备的 | 平台没有为告警记录存设备身份 | 设备可能写在告警文案里,引用时说明「文案里写的是…」并请用户确认 |
| 这条规则失败了多少次 | 规则执行只有 未执行/执行中/已完成 | 说明平台不记录规则失败;不要拿「未执行」充数 |
| 某人的手机号/邮箱 | 联系方式是加密列,不返回 | 指向控制台 |
| 设备的接入密码/密钥 | 任何工具都不返回凭据 | 直接说做不到 |
| 查另一个企业 / 以别人的身份查 | 身份由凭证注入 | 见 [identity-injection](identity-injection.md) |

## 回应形状

三句,缺一句都会留下误解:

1. 这件事平台不记录或不提供(能力边界,不是没查到)
2. 能给到最接近的是什么
3. 准确答案去哪拿

## 清单之外的「查不到」

先分清三种,说法完全不同:

| 情况 | 怎么说 |
| --- | --- |
| 平台不记录这件事 | 能力边界,按上面的回应形状 |
| 该时段确实没有数据 | 是结论,直接回答 |
| 上游暂时不可用 | 说明稍后重试 |

把第三种说成第二种,产出的是一句自信的错误结论。
