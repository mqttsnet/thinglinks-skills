# 工具注册:instructions、annotations、description

模型选哪个工具,依据只有四样:`name` / `title` / `description` / `inputSchema`,
外加服务器级 `instructions`。这五处之外写的东西模型都看不见 —— 包括代码注释、README、需求文档。

## 服务器级 `instructions`

随 `InitializeResult` 下发,客户端注入系统提示。这是**唯一一处「用户什么都没说、模型就知道
该怎么用这套工具」的位置**:用户不会说「请调用 `get_my_permissions`」,只会问
「我为什么看不到这个菜单」。

**加工具必须同步更新这里。** 两个方向都会出事:

- 列出并不存在的工具 → 诱导模型去调,表现为一串找不到工具的报错
- 工具加了却不提 → 模型多半想不到用它,等于白加

这条约束由 `McpServerConfigurationTest` 守着,`SERVER_INSTRUCTIONS` 声明为包级可见即为此。

`instructions` 里只放**工具索引**(name → 一句话职责 + 该工具自己的硬警告)。
排查顺序、判据、措辞纪律不放这里,放 skill 按需加载 —— 全量塞进系统提示会挤占上下文,
而且其中大部分与当前这次提问无关。

## `annotations`

只读查询统一标 `readOnlyHint = true`。客户端据此决定要不要在调用前征求用户确认;
不标的话,只读查询会和写操作一样弹确认,体验直接劣化。

## `description` 写「什么时候用」不写「这是什么」

写「返回设备详情」对选择没有帮助 —— 模型面对的是「这台设备为什么不上报」,不是「请返回设备详情」。
写成「诊断任何设备问题的第一步;判断在线状态、最后心跳、软硬件版本、是否为子设备」才有用。

同一族工具要在 `description` 里点明**彼此的分工**,否则模型只会挑名字最像的:

- 影子答「现在/那一刻是多少」,时序答「这段时间怎么变的」
- `get_my_permissions` 答「我能做什么」,`who_has_permission` 答「谁能做这件事」
- `get_my_recent_operations` 答「我改过什么」,`get_operation_audit` 答「谁改过什么」

## 错误消息要带下一步

工具报错时模型会把错误原样转述给用户。「查询失败」是一条死路;
「单次最多对比 20 台设备,当前 25 台,请分批对比」模型能自己改参数重试。
凡是有上限的入参,都在校验消息里写清上限值与下一步怎么做。

## 无入参工具的 schema

所有「查询本人」类工具都不收参数。身份由凭证确定,**让模型指定查谁等于把越权查询的入口交出去**。
这类工具统一用空对象 schema,不留任何身份类入参。
