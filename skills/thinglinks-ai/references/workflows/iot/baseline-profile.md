# 建立运行基线

基线的用处是给后续所有判断一个参照:没有基线,「30V 算不算高」只能猜。

## 顺序

1. **`get_device`** 拿产品标识与绑定版本 —— 后面每一步都要用
2. **`get_thing_model`** 拿属性清单、单位、量程。**这是基线的骨架**:
   没有单位与量程,统计值只是一串没有意义的数字
3. **`get_metric_stats`** 取要看的属性在目标区间内的条数、均值、实测极值。
   单次最多 8 个属性,属性多就分次
4. **`query_timeseries`** 取其中关键属性的变化过程,用来看周期与形态
5. **`compare_across_devices`** 把同产品同版本的其他设备拉进来横向比

## 一份基线要回答的四个问题

| 问题 | 依据 |
| --- | --- |
| 各属性正常工作在什么区间 | 实测极值与均值,与物模型量程并排 |
| 有没有规律性的波动 | 时序序列的形态(昼夜、班次、周期性充放电) |
| 各属性之间有没有关联 | 两条序列的走势对照 |
| 这台在同类里算不算异常 | 横向对比的排位与被排除的设备 |

## 关于「相关性」和「周期」的说法

这两件事是**在返回的序列上判读出来的,平台不预先计算**。
所以结论要说成「两条序列在该时段走势一致」,而不是「相关系数 0.98」——
除非你确实基于原始上报行算了,并说明算的是哪一段、多少个点。

要自己算就取原始行(时序传原始模式,或影子带时间段),
不要拿窗口聚合的点算 —— 理由见 [orchestration/domains/metric](../../orchestration/domains/metric.md)。

## 条数本身是基线的一部分

上报条数偏少的属性,它的极值不可信 —— 可能只是恰好没采到。
给基线时把条数一并列出,让用户知道哪几个结论的样本量不够。
