# 异常真伪交叉验证

单一信号不足以定性。一个偏高的读数可能是故障,也可能是这台设备的正常工作点、
是采样窗口的边界效应,或者是整批设备都这样。

**这里做的是多源事实交叉,不是时序算法建模** —— 平台不提供分解、变点检测、预测残差这类方法。
说清楚这条边界,比含糊地暗示有算法更可信。

## 五源

| 源 | 回答什么 | 用什么 |
| --- | --- | --- |
| 物理可能性 | 这个值物理上可不可能 | `get_thing_model` 的单位与量程 |
| 实际水平 | 这段时间它实际在什么范围 | `get_metric_stats` 的实测极值与均值 |
| 同类对照 | 别的设备同期是什么样 | `compare_across_devices` |
| 时间对照 | 异常点附近发生过什么 | `get_device` 的版本与连接状态、OTA 记录 |
| 系统性 | 一次性还是持续 | `query_timeseries` 的形态、`get_rule_trigger_stats` 的频次 |

## 定性规则

- **三源指向同一结论** → 可以定性,给结论
- **源之间互相矛盾** → 还没查清,继续查,不要先给结论再补理由
- **只有一源** → 说明当前只有一条证据,以及再查哪一条能定性

## 几种典型组合

| 组合 | 结论 |
| --- | --- |
| 超出量程 + 同产品其他设备正常 + 只出现过一次 | 个体的偶发异常,优先怀疑采集或上报 |
| 超出量程 + 同产品其他设备也超 + 持续出现 | 系统性问题,多半是量纲或配置,不是设备坏 |
| 在量程内 + 偏离本机历史区间 + 与升级时间点接近 | 版本变更引入,走 [fault-triage](fault-triage.md) |
| 在量程内 + 波动有规律 + 与其他设备同步 | 正常工况波动,不是异常 |

## 别把边界当异常

序列首尾的点、刚上电的第一批上报、窗口切分处,常常出现看起来突兀的值。
断言异常之前先确认它不在这些位置上。
