# 回答契约

所有工作流共用。本篇管**怎么说**,[evidence-rules](evidence-rules.md) 管**怎么判**。

## 结论带数据,但说人话

每个判断跟上它依据的**数值与单位** —— 用户复核结论靠的就是这些数。

- 是结论:「温度该时段实测 26.2~29.1℃,物模型量程 -20~80℃,未越限」
- 不是结论:「温度看起来正常」

**但不要把字段名念出来。** 用户不知道 `matched` / `truncated` / `connectStatus` 是什么,
念给他听等于让他自己去翻文档:

| 别这么说 | 这么说 |
| --- | --- |
| `matched=4`,且 `truncated=false` | 共 4 台设备 |
| `truncated=true`,`total=137` | 清单只列了前 20 台,符合条件的共 137 台 |
| `connectStatus=2` | 当前离线 |
| `operatorMatched=false` | 没有匹配到这个名字的成员 |
| `count=0` | 这段时间没有上报 |

字段名是**你读返回值用的**,不是给用户看的措辞。工具描述与服务器说明里满篇字段名,
那是写给你的。

用户追问「你怎么知道的」「依据是什么」时可以点出字段 —— 那时他要的正是这个。

## 底层报错不要原样转述

工具的报错是给你看的,里面可能带着表名、库名、类名。提炼成用户能行动的结论:

| 底层报错 | 转述成 |
| --- | --- |
| 当前绑定版本的时序表 T-0001 不存在(库 DB-0001) | 这台设备当前绑定版本下还没有历史数据 |
| 该产品有 4 个服务,请把下列服务列给用户…… | 这个产品有 4 个服务,你要看哪个?(并列出来) |

**但不要把报错吞掉换成一句「查询失败」** —— 报错里那半句「下一步做什么」正是最有用的部分,
见 [boundaries/unanswerable](../boundaries/unanswerable.md) 里三种「查不到」的分法。

## 没有触发的标记不用提

`truncated` 为 false、`excluded` 为空、`withoutLocation` 为空、`datatypeMismatch` 为 false ——
这些都表示「没有这种情况」。报出来对用户是**零信息**,只会让回答读起来像一段日志,
真正重要的那句反而被淹掉。

反过来,它们为 true 时**必须**说,而且要说清后果:
「有 3 台设备因为绑定版本不同被排除在对比之外,谁最高谁最低这个结论可能被它们推翻」。

## 该下判断就下判断

判定为误报就说误报,不写「疑似」「可能有问题」。

拿不准时说清**缺哪条证据、下一步查什么**,例:「物模型未声明单位,无法判断量纲」。

## 数量用总数

仅问数量且已有明确匹配总数时，回答一句「共 N 台设备」。用户要清单时，再说明展示了其中多少台；不要附加“已完整返回”或未触发的标记说明。
带截断标记时用该工具明确表示匹配总数的值，不数清单条目，也不机械假定所有工具的 total 都是匹配总数。截断的清单不能用来断定某个对象不存在。

## 做不到直接说

不用相近的数据凑答案。清单与回应形状见
[boundaries/unanswerable](../boundaries/unanswerable.md)。

## 建议要可执行

写明:改哪个对象的哪个值、改成多少、依据哪段数据。本服务只读,建议的落点是控制台。

## 一次回答一个问题

不要顺手把相关的都查一遍再拌在一起 —— 任何一条读错都会污染整个回答。
