# 云控定位、结果与回执

## 先回答实际执行了没有

命令超时后，先找原命令标识、目标设备/服务/命令、时间和设备当前状态。重启不是重试依据；在不知道是否执行时，不能自动再次写入。

```text
Cloud 下发 → 网关 command → CommandBridge 校验/去重 → 唯一活跃消费者
→ 一次租约 → 协议写入 → 执行结果 → 独立发送 commandResponse
```

Cloud 标准 Topic、身份和回执合同见 [云端协同](../../thinglinks-cloud/references/iot/edge-integration.md)。普通用户只需选择设备、命令和参数，无需手写 Topic 或信封。

## 按状态定位

| Edge 状态/现象 | 含义与下一步 |
| --- | --- |
| 找不到命令 | 核对 Cloud 发送证据、网关订阅、子设备身份和时间；先不归因于 PLC |
| rejected | 看明确拒绝原因：模型/参数、离线或过期、无消费者/多消费者等 |
| queued | 已进入队列，检查目标流程声明、有效绑定与领取；不等于已交设备 |
| leased | 消费者已领取，核对租约截止、协议请求和结果；不可并发重发 |
| succeeded | 该协议适配已取得执行成功证据；需要业务效果时另看设备读回/状态 |
| failed | 已明确失败或拒绝，按具体错误处理，仍不无限重试 |
| unknown | 可能已执行但确认丢失；先查设备结果、原请求和协议日志 |
| replyPending / replyError | 执行结果与回执传输分开；修复回执发送不重新执行写入 |

每个控制目标按设备、服务、命令和参数精确映射。同目标多条活跃流程会被视为歧义，不会自动选其中一条。停用流程的绑定需等待有效期/清理，不靠复制流程抢占。
去重记录和执行状态持久化，有容量/历史窗口。不要删命令记录、恢复旧库或改 `mid` 来绕过去重；未知的外部设备动作无法靠数据库回滚撤销。

## 配置和协议检查

- 先读该设备绑定版本的命令定义，确认参数编码、单位、类型、范围和必填项。MCP 当前模型不等于任意历史绑定版本，见 [云边对齐](cloud-integration.md)。
- 控制值按 `(工程值 - 偏移) / 倍率` 反算。倍率为零、整数写入出现小数、超范围或不明确映射时拒绝，不“修正成大概能用”的值。
- TCP/UDP 控制模板要求设备返回匹配的 `requestId` 与明确 `ok:true`；厂商协议不符合时需专门适配。
- HTTP 200 还需约定的执行确认字段为布尔 true；202 只表示接受/排队，不能作执行成功。
- S7 等待写节点驱动完成，不能把请求入队当成功。
- OPC UA 要对应目标和 Good 写结果；明确 `BadWriteNotSupported` 为失败。不匹配或不完整结果仍为 unknown。组件相对超时不能保证取消已发出的设备写入。
- Modbus-TCP 新内置控制被禁用。旧保存快照和已部署流程不会自动撤销迟到写请求，应按明确的维护范围停用/替换并验证。

## Cloud 历史的特殊边界

当前核对的 Cloud `CommandResponseHandler → EventCommandService` 会保存独立响应记录，按 Topic 路径的网关身份归属；不是按 `head.mid` 更新原下发记录。
因此子设备命令历史里没见响应，不能直接推出“设备从未回应”；同时检查网关响应记录、报文里的子设备、`mid/serviceCode/cmd`、业务结果与 Edge 执行记录。
响应记录的存储状态成功只表示响应已记录，实际业务错误仍须读响应内容；原记录 `respondedTime` 为空不能单独证明 PLC 未执行。内容截断或脱敏时明确缺少关联证据。

## 可交给用户的下一步

给出一条具体动作及验收值，例如：“这条命令为 unknown，现场读回已经是目标 52℃，先保留原记录并查回执错误，不重发设备写入。”
若确需新控制动作，明确目标、工程值、动作影响和现有授权；当前 ThingLinks MCP 只能查询定义/历史，不能执行下发。用户可在正式控制台操作，随后继续核对实际执行和回执。

依据：Edge `apps/manager/src/core/cloud/commands/{bridge,types,model-validation}.ts`、`apps/manager/src/core/flows/templates/control-*.ts`、`apps/manager/src/core/cloud/mid.ts`；Cloud 服务端入口见云端协同篇。
